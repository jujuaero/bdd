DAOs JDBC (couche de persistance):
- `JdbcArtistDao` (findAll, save, update, delete, findByCity)
- `JdbcArtworkDao` (findAll, save, update, delete, findByArtistName)
- `JdbcCommunityMemberDao` (findById, findAll)
- `JdbcGalleryDao` (findById, findAll)
- `JdbcExhibitionDao` (findAll, save, update, delete)
- `JdbcWorkshopDao` (findById, findAll)
Tous utilisent PreparedStatement, try-with-resources, gestion d'errours SQLException.

Services JDBC (couche applicative):
- `JdbcArtistService` (getAllArtists, getArtistByName, createArtist, updateArtist, deleteArtist, getAllDisciplines, searchArtists)
- `JdbcArtworkService` (getAllArtworks, getArtworkByTitle, getArtworksByArtist, createArtwork, updateArtwork, deleteArtwork)
- `JdbcCommunityService` (getAllMembers, getMemberByName, getReviewsByMember)
- `JdbcGalleryService` (getAllGalleries, getGalleryByName, getExhibitionsByGallery)
- `JdbcWorkshopService` (getAllWorkshops, getWorkshopByTitle, bookWorkshop, getBookingsByMember)

Basculement dynamique:
- `ServiceProvider` : quand `usePersistence=true` dans `database.properties`, les getters de service retournent des instances JDBC
  (ArtistService, ArtworkService, CommunityService, GalleryService, WorkshopService) au lieu des implémentations InMemory.
- Fallback automatique vers InMemory si JDBC échoue à l'initialisation.

Architecture JDBC (résumé)
1. Database layer (DAO): Directement sur les tables MySQL (artist, artwork, gallery, exhibition, workshop, community_member, etc.)
2. Service layer: Agrège les DAOs et fournit les interfaces métier (ArtistService, ArtworkService, etc.)
3. UI layer: Appelle ServiceProvider.getXxxService() qui retourne le service JDBC ou InMemory selon configuration
4. Configuration: DatabaseConfig lit `database.properties` (URL, USER, PASSWORD, USE_PERSISTENCE)

Schéma des relations:
- Artist --[1:N]--> Artwork (FK artist_id dans artwork)
- Artist --[N:M]--> Discipline (table artist_discipline)
- Gallery --[1:N]--> Exhibition (FK gallery_id dans exhibition)
- Exhibition --[N:M]--> Artwork (table exhibition_artwork)
- Artwork --[1:N]--> ArtworkTag (FK artwork_id dans artwork_tag)
- Workshop --[instructor = Artist] (FK instructor_id dans workshop)
- Workshop --[1:N]--> Booking (FK workshop_id dans booking)
- CommunityMember --[1:N]--> Booking (FK member_id dans booking)
- CommunityMember --[1:N]--> Review (FK reviewer_id dans review)
- Artwork --[reviewers]--> Review (FK artwork_id dans review)
- CommunityMember --[N:M]--> Discipline (table member_favorite_discipline)

   - user=<votre_user_mysql>
   - password=<votre_password_mysql>
   - usePersistence=true (pour activer l'utilisation des services JDBC)

Remarques finales
=================
- Les services JDBC et les DAO utilisent les identifiants naturels (name/title/email) fournis par les modèles.
- Si un champ est NULL dans le modèle lors d'une insertion, il sera NULL en base. Pour éviter cela, validez/remplissez tous les champs avant create/update depuis l'UI.
- Les relations N-N (artist_discipline, exhibition_artwork, artwork_tag, member_favorite_discipline) ne sont pas gérées automatiquement lors des inserts. Elles peuvent être ajoutées si nécessaire.
- Le script datav3.sql remplit la base avec des données de test cohérentes (pas de NULLs explicites, respecte les FK).
- En production, envisagez un pool de connexions (ex. HikariCP) à la place de DriverManager.getConnection().
